--------------------------------------------------------------------------------
1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
--------------------------------------------------------------------------------
Nightcode is designed as a terminal-native AI coding assistant supporting complex 
project development across CLI (`@nightcode/cli`), server (`@nightcode/server`), 
and database (`@nightcode/database`).

Currently, conversation history is stored as a single monolithic JSON blob inside 
a single database row in PostgreSQL:
  `Session.messages` (Json column in `packages/database/prisma/schema.prisma`)

While this design is simple for prototyping, it poses severe scalability, 
performance, and reliability bottlenecks as users run Nightcode on complex codebases.

--------------------------------------------------------------------------------
2. IN-DEPTH ANALYSIS OF THE MONOLITHIC ROW ISSUE
--------------------------------------------------------------------------------
In coding assistant sessions, AI tools (such as `readFile`, `writeFile`, `grep`, 
`listDirectory`, and `bash`) produce large text outputs:
  - `readFile`: May output hundreds or thousands of lines of code per call.
  - `bash`: May capture extensive stdout/stderr output from build scripts or tests.
  - `reasoning`: AI thinking blocks may span thousands of tokens.

Under the current architecture (`Session.messages` JSON array):
1. Exponential Data Bloat:
   Every tool execution appends output directly into message parts:
   `parts: [{ type: "tool-readFile", output: { content: "...100KB of source..." } }]`
   A single session in a real-world coding project can easily grow to tens of 
   megabytes per database row.

2. PostgreSQL TOAST & Database Overhead:
   PostgreSQL stores rows larger than ~2KB in TOAST (The Oversized-Attribute 
   Storage Technique) tables. Loading or updating a row forces PostgreSQL to 
   decompress and re-serialize the entire JSON array on every query.

3. Full Table Write-Back Overhead:
   In `packages/server/src/routes/chat.ts`, upon completing an AI stream, the 
   server executes:
     `await db.session.update({ where: { id }, data: { messages: event.messages } });`
   This rewrites the ENTIRE array of past messages to disk, even if only 1 new 
   message or tool output was appended.

4. Network & Memory Strain:
   `GET /sessions/:id` returns the full session object including all historical 
   messages. Over time, fetching a session causes high memory spikes on both 
   the Hono server and OpenTUI CLI, slow initial render times, and high network payload size.

5. Race Conditions & Concurrency Risks:
   Without optimistic locking (`@version`), if two tool outputs or messages are 
   processed concurrently, the last write-back will overwrite the entire 
   `messages` array, causing silent message data loss.

--------------------------------------------------------------------------------
3. PROPOSED SOLUTIONS & ARCHITECTURAL REFACTORING
--------------------------------------------------------------------------------

[RECOMMENDATION A] Relational Schema Normalization (Session -> Message -> ToolOutput)
--------------------------------------------------------------------------------
Transform the monolithic `Session` model into a normalized relational model.

Prisma Schema Proposal:
```prisma
model Session {
  id        String    @id @default(cuid())
  userId    String
  title     String
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  messages  Message[]

  @@index([userId])
}

model Message {
  id        String   @id @default(cuid())
  sessionId String
  session   Session  @relation(fields: [sessionId], references: [id], onDelete: Cascade)
  role      String   // "user" | "assistant" | "system"
  order     Int      // Sequential message index
  metadata  Json?    // { mode, model, durationMs, usage }
  parts     Json     // Message parts array (or normalized MessagePart table)
  createdAt DateTime @default(now())

  @@index([sessionId, order])
}
```

Benefits:
- Atomic Inserts: Adding a new message requires only `db.message.create()`, avoiding updating past messages.
- Paginated Retrieval: The CLI can load recent messages (`GET /sessions/:id/messages?limit=20&cursor=...`) on screen load and lazily fetch older history when scrolling up.
- Minimal Payload for Session Listing: `GET /sessions` only selects metadata (`id`, `title`, `updatedAt`), eliminating JSON overhead.

[RECOMMENDATION B] Payload Truncation & External Artifact Storage
--------------------------------------------------------------------------------
- Store huge tool execution outputs (e.g. `readFile` contents > 50KB or `bash` logs) in an Object Store / KV Store or truncated summary fields in the primary message DB.
- Keep full tool output references in local CLI cache or secondary blob table, returning light references to the LLM context and DB storage.

[RECOMMENDATION C] Optimistic Concurrency Control
--------------------------------------------------------------------------------
- Add a `@version Int @default(1)` field or `updatedAt` checking on the `Session` model to prevent concurrent chat write-backs from overwriting session history.

[RECOMMENDATION D] OpenTUI Terminal Rendering Virtualization
--------------------------------------------------------------------------------
- In `@nightcode/cli`, virtualize or cap the rendered message buffer in `bot-message.tsx` and `inputBar.tsx` so long terminal strings do not degrade OpenTUI 60 FPS rendering performance.

[RECOMMENDATION E] Model Context & Token Truncation Middleware
--------------------------------------------------------------------------------
- Introduce system prompt payload capping in `packages/server/src/routes/chat.ts` to automatically prune obsolete or repetitive tool outputs before passing history to Vercel AI SDK (`convertToModelMessages`).

--------------------------------------------------------------------------------
4. MIGRATION & IMPLEMENTATION STEPS
--------------------------------------------------------------------------------
To execute this refactoring in accordance with Nightcode Coding Standards (docs/05-coding-standards.md §12 Task F):

1. Shared Contracts (`packages/shared`):
   - Update message and session schemas to support paginated fetching and incremental message insertion.
2. Database Package (`packages/database`):
   - Add `Message` model to `schema.prisma`.
   - Run `bun run --cwd packages/database db:generate` to update Prisma client.
   - Create data migration script to migrate existing `Session.messages` JSON arrays into `Message` rows.
3. Server Package (`packages/server`):
   - Refactor `GET /sessions/:id` and add `GET /sessions/:id/messages`.
   - Update `POST /chat` to append new messages incrementally to the `Message` table instead of re-saving the entire `Session.messages` array.
4. CLI Package (`packages/cli`):
   - Update `useChat` hook to consume paginated message endpoints.

--------------------------------------------------------------------------------
5. CONCLUSION
--------------------------------------------------------------------------------
Resolving the monolithic `Session.messages` JSON row issue will dramatically improve 
Nightcode's stability, response latency, database scalability, and TUI smoothness, 
ensuring seamless performance even for enterprise-scale software projects.
